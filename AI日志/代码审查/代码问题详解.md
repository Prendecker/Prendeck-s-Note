## 坑 1 · `Item.value` 连续赋值两次

**位置**：5 个武器文件各一处

| 文件 | 行 |
|---|---|
| `Content/Items/Weapons/Melee/Sigkin.cs` | 30-31 |
| `Content/Items/Weapons/Ranged/B_Gun.cs` | 26-27 |
| `Content/Items/Weapons/Magic/Test_One.cs` | 28-29 |
| `Content/Items/Weapons/Summon/Minions/Test_Two.cs` | 25-26 |
| `Content/Items/Weapons/Summon/Marking/The_Poorly_Painted_Brush.cs` | 29-30 |

### 现象

五个文件的写法**一模一样**，都是先 `sellPrice` 再 `buyPrice`：

```csharp
Item.value = Item.sellPrice(1, 0, 0, 0);
Item.value = Item.buyPrice(1, 0, 0, 0);
```

后一行把前一行**整个覆盖掉**，第一行等于白写。

「被鸽的画笔」最明显，它本来想卖 7 银，结果变成 **0 元**：

```csharp
Item.value = Item.sellPrice(0, 0, 7, 0);   // 想卖 7 银
Item.value = Item.buyPrice(0, 0, 0, 0);    // 被覆盖成 0
```

### 原理

`Item.value` 是**同一个字段**。赋值两次，就是第二次赢 —— 这跟"用两种方式设置同一个东西"是两码事。

`buyPrice` 和 `sellPrice` 不是两种"设置方式"，而是两种**不同的意图**：

- `buyPrice` = 这东西**买进来**要多少钱
- `sellPrice` = 这东西**卖出去**能得多少钱

**最容易踩的坑在这儿**：`sellPrice` 的返回值是 `buyPrice` 的 **5 倍**。

所以写两行不只是"多写一行" —— 你实际上把物品价格**偷偷改成了原本意图的 1/5**。

### 怎么自己查证

```bash
python Tools/api_lookup.py Item.sellPrice
python Tools/api_lookup.py Item.buyPrice
```

跑完你会看到官方原文：

> **buyPrice**：*"If assigned to `Item.value`, that item will be **bought** for the provided value."*
>
> **sellPrice**：*"If assigned to `Item.value`, that item will be **sold** for the provided value. This value is **five times larger** than `Item.buyPrice`."*

「five times larger」这五个字，就是我上面那句"5 倍"的出处。

### 怎么改

**二选一，只留一行**：

- 想让它**卖** 1 铂金 → 只写 `Item.sellPrice(1,0,0,0)`
- 想让它**买** 1 铂金 → 只写 `Item.buyPrice(1,0,0,0)`

⚠️ **五个文件改法不一样**，别无脑统一：

- **「被鸽的画笔」要保留 `sellPrice`** —— 因为 `buyPrice(0,0,0,0)` 让它变成 0 元，明显不是本意
- **其余四个测试武器保留哪个都行** —— 看你想让它值多少钱

**已改的版本**：测试武器保留了 `buyPrice`（保持游戏内表现不变），画笔保留了 `sellPrice`（修掉 0 元）。

## 坑 2 · en-US 本地化的坏键引用

**位置**：`Localization/en-US_Mods.PrendeckOddments.hjson` 的 `Buffs` 段

### 现象

```hjson
Buffs: {
    Soul_Burn_Buff: {
        DisplayName: Soul Burn
        Description: Mods.PrendeckOddments.Buffs.SoulBurnBuff.Description   # ← 问题在这
    }
}
```

游戏里燃魂 Buff 的描述位置，会**原样显示这串键名**：

```
Mods.PrendeckOddments.Buffs.SoulBurnBuff.Description
```

而不是任何说明文字。**这是会直接暴露给玩家的低级错误。**

### 原理

tModLoader 的本地化键**按类名索引**。

这个 Buff 的类名是 `Soul_Burn_Buff`（**带下划线**），而这里写的是 `SoulBurnBuff`（**没下划线**）—— 指向了一个**根本不存在的键**。

tModLoader 找不到键时的行为是：**把键名原样显示出来**（而不是显示空白或报错）。所以这个错误会非常显眼。

### 怎么自己查证

直接搜本地化文件里有没有残留的坏键：

```bash
grep -n "SoulBurnBuff" Localization/*.hjson
```

改之前跑，你能看到它；修好之后再跑，应该什么都不输出。

> 顺带一提：`Soul_Burn_Buff` 这种**带下划线的类名**是社区教程的常见风格，但不符合 C# 惯例（C# 通常用 `SoulBurnBuff`）。你的项目里大量用了这种风格 —— 不是错误，但要知道它会让本地化键变得容易写错（这个坑就是活例子）。

### 怎么改

两个选择：

1. **写正常的英文描述**（推荐）
2. **删掉这一行** —— 但这样 Buff 就没描述了

**已改的版本**：写成了正常英文，对应中文版的意思（65% 伤害 / 45% 暴击 / 持续掉血）。

## 坑 3 · `SetWeaponValues` 参数注释标错

### 现象

多个武器文件里都有这行，注释是**错的**：

```csharp
Item.SetWeaponValues(114514, 1000, 100); //设置伤害，暴击率，射速
```

三个参数里**错了两个**。

### 原理

真实签名是：

```csharp
void SetWeaponValues(int dmg, float knockback, int bonusCritChance)
```

是**伤害、击退、暴击率**，不是"伤害、暴击率、射速"。

**为什么这条值得单列**：注释是**写给未来的自己看的**。参数顺序记错 + 注释也写错 = **双重误导**。以后你照着这条注释写新武器，会把击退值填到暴击率的位置上，然后奇怪为什么武器手感不对。

**讽刺的是**：`The_Poorly_Painted_Brush.cs:20` 里你自己**写对了**（`//设置伤害，击退，暴击率`）—— 说明你后来学会了，只是早期文件没回头改。

> 💡 **这条最值得学的是**：改 API 用法时，**顺手把注释一起改**。注释腐烂比代码腐烂更危险，因为代码错了编译器会报错，注释错了没人提醒你。

### 怎么自己查证

```bash
python Tools/api_lookup.py SetWeaponValues
```

输出：

```
void SetWeaponValues(int dmg, float knockback, int bonusCritChance = 0)
  This method conveniently sets Item.damage, Item.knockBack, and Item.crit.
```

官方摘要里那三个字段的顺序，就是参数的顺序。

### 怎么改

**只改注释，不要动数值** —— 动数值会改变游戏手感。

以此类推，把三个参数对上：`dmg` → 伤害、`knockback` → 击退、`bonusCritChance` → 暴击率。

## 坑 5 · 测试数值未平衡

### 现象

原因是击退值直接进物理计算 —— 原版武器击退一般在 `0` ~ `20` 之间，`1000` 会让敌人**直接飞出屏幕**。实战里你甚至可能打不中第二下，因为怪已经不见了。

```bash
python Tools/api_lookup.py SetWeaponValues
```

再用原版武器对照：去游戏里看一把原版武器的 tooltip，或者查 `百科\ExampleMod` 里的武器数值。

### 怎么改

**先定这模组的定位**。你笔记里写的是"**超模 + 娱乐向**"，那么数值偏高是**合理的**，但要注意：

- 超模 ≠ 破坏体验。`5000` 伤害已经能秒杀大部分原版 Boss，`114514` 纯粹是玩梗
- **击退建议先拉到正常范围**（0~20），这是性价比最高的一步
- 真要保留梗数值，可以考虑做成"**开发者武器**"（像原版的 `Zenith` 那样单独定位）

## 坑 6 · XML 文档注释闭合标签写错

**位置**：`Content/LIVG_PIIU_GLue.cs:7-9` 和 `32-35`

### 现象

```csharp
///<summary>
///修改原版3个骗伤弹幕并注入一些咒骂re的话
///<summary>          ← 注意这里
```

开标签和闭标签**都写成了 `<summary>`**，闭标签少了个斜杠 `/`。

### 原理

C# 的 XML 文档注释用 `///` 开头，标签规则和 XML 一样：

- 开标签：`<summary>`
- 闭标签：`</summary>` ← **必须有斜杠**

写错之后，**编译器不报错**（毕竟它只是注释），但 IDE 解析不出来 —— 结果就是**鼠标悬停在这个类上时，不会显示这段说明**。

等于你辛辛苦苦写的注释，**白写了**。

### 怎么自己查证

没法用 `api_lookup.py` 查（那是查 API 的）。但可以：

1. 在 Visual Studio 里把鼠标悬停在 `LIVG_PIIU_GLue` 这个类名上
2. **修好前**：不显示注释内容
3. **修好后**：正常显示

### 怎么改

闭合标签写成 `///</summary>`。注意 `///` 和 `<` 之间通常加个空格更规范：`/// <summary>`。

**你的 `Toy_Knife.cs` 里就写了几个合格的例子**（虽然没用 `<summary>` 标签，但用了 `//` 行内注释，至少不会误导）。

✅ **已修**（2026-09-25，用户自己把两处闭合标签改成了 `///</summary>`）。

## 坑 7 · 未使用的 using

**位置**：

- `Content/Projectiles/Ammo_Proj/Gravel_Bullet_Proj.cs:2` —— `using System.Net.NetworkInformation;`
- 3 个文件里的 `using Terraria.Graphics.Shaders;`

### 现象

`System.Net.NetworkInformation` 是**网络信息**相关的命名空间（ping、网卡状态之类），跟一个弹幕**八竿子打不着**。

八成是 IDE 自动补全时手滑点错了 —— 你打个 `using System.Net.` 它就弹一堆出来。

`Terraria.Graphics.Shaders` 则是**想写 shader 但没写成**留下的。

### 原理

完全无害 —— C# 编译器会忽略没用到的 `using`，不影响性能也不影响运行。

**但它会误导读者**：看到 `using System.Net.NetworkInformation` 的人会以为这文件涉及网络通信，翻半天找不到。

### 怎么自己查证

看这个 using 里的类型在文件里有没有被用到。比如 `NetworkInformation` 里的 `Ping`、`NetworkInterface` 这些词，全文搜一下 —— 搜不到就是没用。

Visual Studio 会把未使用的 using **置灰**，也是个直观信号。

### 怎么改

删掉即可。VS 有快捷键可以一次性清理（右键 → 移除和排序 Using）。

## 坑 9 · 空重写

**位置**：`Content/Projectiles/Sigma.cs:46-49`

### 现象

```csharp
public override bool PreKill(int timeLeft)
{
    return base.PreKill(timeLeft);   // 只调了 base，什么也没做
}
```

整个方法**删掉，行为完全一样**。

### 原理

`PreKill` 的作用是**拦截**：返回 `false` 可以阻止原版的死亡逻辑和 `OnKill` 钩子被调用。

官方原文：

> *"Allows you to determine whether the vanilla code for Kill and the Kill hook will be called. Return false to stop them from being called. **Returns true by default.**"*

你这个重写**原样返回了默认值**，等于没拦任何东西。

**为什么这值得单独讲** —— 它涉及一个通用原则：

> **什么时候该调 `base`，什么时候不该？**

- ✅ **该调 `base`**：你在原有行为**之上加东西**（比如 `AI()` 里先加自己的逻辑，再 `base.AI()`）
- ❌ **不该调 `base`**：你要**完全替换**原有行为（比如自己实现了整套追踪 AI，就不该再调 `base.AI()`，否则会打架）
- ⚠️ **只调 `base` 其余啥都不干**：**直接删掉整个方法**

你的 `Toy_Star_Fragments.cs` 里那个完整的追踪 AI，就是"不该调 base"的正确例子。

### 怎么自己查证

```bash
python Tools/api_lookup.py ModProjectile.PreKill
```

顺便对比一下**一个有实际内容的钩子**长什么样：

```bash
python Tools/api_lookup.py ModProjectile.OnKill
```

```csharp
void OnKill(int timeLeft)
  Allows you to control what happens when this projectile is killed
  (for example, creating dust or making sounds). Also useful for creating retrievable ammo.
```

对比一下就看出来了：`OnKill` 是**你真的要做点什么**，`PreKill` 是**你要不要拦截**。什么都不拦截就没必要写。

### 怎么改

删掉整个方法。

## 坑 11 · 缩进混用

**位置**：全项目

### 现象

- `Sigkin.cs` 用 **Tab 缩进**
- 多数文件用 **4 个空格**
- 部分文件内部还混着两种

### 原理

在编辑器里看会歪歪扭扭 —— 因为 Tab 的显示宽度**取决于编辑器设置**（有人设 4 格，有人设 8 格），而空格宽度固定。

**为什么这会让 Git diff 变脏**：如果你改了一行，缩进从 Tab 变成空格，diff 会显示"整行都变了"，实际逻辑没变。以后你用了版本控制，这会很烦。

### 怎么自己查证

Visual Studio：**编辑 → 高级 → 查看空白**（或快捷键 `Ctrl+R, Ctrl+W`），空格显示成点、Tab 显示成箭头，一眼看出来。

### 怎么改

统一成 **4 个空格**（C# 社区惯例）。

## 附录 B · `Toy_Knife` 的 `[0]` 占位符 —— 是正确写法

### 情况

`Toy_Knife.cs:23-38` 用了两个不同的占位符，我一度以为是 tModLoader 1.3 的旧语法残留。

### 结论：**这是有意设计，而且是正解**

```csharp
// {0} → 由 WithFormatArgs 注入「固定回蓝量」
public override LocalizedText Tooltip => base.Tooltip.WithFormatArgs(MANA_Regen);

// [0] → 由 ModifyTooltips 手动替换成「实际魔力消耗」
public override void ModifyTooltips(List<TooltipLine> tooltips)
{
    int R_MANA = (int)(MANA * player.manaCost);   // 算了玩家的魔力减免
    foreach (var item in tooltips)
        if (item.Text.Contains("[0]"))
            item.Text = item.Text.Replace("[0]", R_MANA.ToString());
}
```

### 为什么必须这么写

这两个值**根本不一样**：

| 占位符 | 显示什么 | 值从哪来 |
|---|---|---|
| `{0}` | **固定回蓝量** | `MANA / 5`，编译期常量 |
| `[0]` | **实际魔力消耗** | `MANA * player.manaCost`，**运行时才知道** |

关键在最后那句 —— 实际消耗要乘以玩家的 `manaCost` 减免（装备/饰品会改变它），**这个值只有生成 tooltip 时才拿得到**。

而 `WithFormatArgs` 是在**属性初始化时**求值的（`public override LocalizedText Tooltip => ...`），那时候**根本不知道玩家是谁**，更不知道他的魔力减免。

所以「**自定义占位符 + `ModifyTooltips` 手动替换**」是这套 API 下的**标准解法**。

### 附带说明

`Toy_Knife.cs:38` 那句暴躁的注释：

```csharp
//去你妈的我甚至还得专门写一套文本同步，"ITEM.MANA"FUCK YOU
```

现在回头看，**你当时的做法是对的** —— 只是可能没意识到为什么必须这么做。这就是原因。

# 🛠 附：怎么自己查 API

配套工具在模组目录下的 `Tools/`：

```bash
python Tools/api_lookup.py ModItem.Shoot         # 查单个钩子
python Tools/api_lookup.py --type ModProjectile  # 列出一个类所有可 override 的钩子
python Tools/api_lookup.py --overridable OnHit   # 搜所有带 OnHit 的钩子
python Tools/api_lookup.py --ns                  # 列出所有命名空间
python Tools/api_lookup.py --refresh             # tModLoader 更新后重新导出索引
```

> `Tools/` 已在 `.csproj` 里整体排除，不会参与模组编译打包。

**输出里 `▸` 标记 = 「可以 override」** —— 这是模组开发最关心的信息。

**数据来源（全本地、零网络）**：

1. `..\..\tModLoader\tModLoader.xml` —— 官方文档，4967 条
2. `Tools/api_index.json` —— 反射 `tModLoader.dll` 生成，提供官方 XML **缺失的返回值类型**

**为什么非要反射不可**：官方 XML 只记参数类型，**不记返回值**，2204 个方法里只有 477 个有 `<returns>` 说明（21%）。
而返回值在 tModLoader 里极其关键 —— 比如 `ModItem.Shoot` 返回 `bool`，`return false` 表示"我手动发射过了，别再自动射一发"。
